### 项目与协作

### 用户与终端

- 一期聚焦 Java 后端，覆盖初级、中级、高级。
- 支持电脑 Web 与微信小程序。
- 必须登录，两端共用账号与数据。

### UI 方向

- 采用专业简洁风格：浅色背景、清晰的流程与反馈卡片，突出问题、回答和进度。
- 用户已确认六页结构：工作台、简历导入与确认、对话式面试准备（含大纲确认）、面试室、复盘报告、设置。
- 用户已确认 Web 面试室采用左侧流程、中间问答与语音操作、右侧反馈；小程序单列问答、底部语音操作、顶部阶段进度，流程按需展开。
- 授权制作第一版示例数据交互原型，优先验证准备面试、确认流程、回答和反馈；尚未授权进入真实业务实现。

### 面试准备

- 支持导入简历，由 LLM 先分析内容。
- 一期支持 PDF、Word（DOCX）、Markdown（.md）、纯文本（.txt）文件及粘贴文本输入。
- 简历解析后展示结构化结果，允许用户确认与修正。
- 在对话页询问目标岗位与考察偏好；目标岗位 JD 可选提供。
- 结合简历、岗位内容生成技术方向选项，允许多选，并给出相关提示或推荐依据。
- 方向示例：JVM、分布式事务、并发、多线程、AI 等；实际选项应由岗位与简历驱动。
- 用户选择后可以自由补充诉求。
- 围绕选定技术大类生成基础原理题（八股文）及业务场景题。
- 面试前以流程图告知整体流程。
- 开始前选择陪练模式或模拟面试模式。
- 时长采用档位：15 分钟专项、30 分钟标准、45 分钟深度。

### 面试交互与编排

- 一期只做语音问答，不包含代码阅读题或在线编程。
- 按轮次对话：面试官播报问题，用户点击开始回答，实时转写，用户点击回答完成后系统处理。
- 用户手动控制每个问题、每个环节的开始和结束。
- 基本环节：自我介绍、技术问题、业务问题、HR 问题（如离职原因）。
- 问题必须有强条理性，环环相扣、层层递进，由技术到业务到个人。
- 通常每道主问题追问 3—4 次，依据难度和回答情况调整。
- 追问综合简历、面试大纲和候选人的实际回答生成。
- 自我介绍结束后，依据新增内容修改后续题目大纲或补充问题。
- 陪练模式的大纲调整由用户确认；模拟面试模式自动调整。

### 反馈与评价

- 陪练模式每次回答结束后评分、指出问题并提供优化意见，包括追问回答。
- 模拟面试模式整场结束后统一展示评价。
- 需要多维度评价，具体评分权重、量表和报告结构仍待设计确认。

### 数据保存

- 默认保存面试转写和评价。
- 回答录音是否保留由用户选择，不默认长期保存。
- 录音保留选项的作用范围、保存期限和删除机制尚待设计确认。

### 模型与设置

- 接入大模型与实时语音对话能力。
- 一期考虑 GLM、DeepSeek、Qwen 三个厂商的 API 接入标准；各厂商实际支持能力需在技术选型时核对官方文档。
- 平台提供默认模型，用户也可以在设置页自定义 API。
- 默认模型供应商、具体模型、语音链路、自定义配置范围及费用规则尚未确定。

### 风格选项与管理员提示词管理

- 普通用户通过选项选择面试风格，不直接编辑底层提示词；自定义 API 配置仍保留。
- 风格维度包括面试官表达、考察倾向、追问策略和反馈详略；设置页保存默认值，准备页可调整本场配置。
- 风格不改变评分标准，不覆盖模拟模式隐藏反馈、禁止解题提示等规则。
- 增加管理员账号与独立 Web 管理入口，真实产品由服务端校验权限。
- 管理员可管理 P01—P10 全部任务模板：简历理解、岗位分析、需求澄清与方向推荐、大纲规划、自我介绍后调整、主问题生成、回答评价、追问、辅导优化、复盘报告。
- 管理员支持编辑基础提示词、风格规则及评价规则，查看上下文变量，维护草稿、示例测试、发布版本、修改记录和回滚。
- 请求由任务模板、风格规则、本场配置及面试上下文组合；模式隔离、权限和输出结构校验由程序负责。
- 修改不立即影响用户。采用草稿 → 测试 → 发布流程，新面试使用新版本，已开始的面试锁定版本；历史报告可追溯。
- 具体风格选项文案、模板内容和管理员页面细节通过原型继续评审。

## 已提出但尚未最终确认的设计建议

- 评分维度：切题与完整性、专业准确性、分析与推理、方案与取舍、项目深度与贡献、证据与一致性、表达与结构、沟通与反思。
- 评分提供回答证据、理由、改进建议与置信度；未考察项不计零分；区分语音识别错误和知识错误。
- 陪练支持重答，分开记录首次表现与获得提示后的表现。
- 大纲调整只影响未开始内容，保存变更原因与历史。
- 时长作为规划预算，到时提示收尾而非强制截断；陪练反馈阅读与重答耗时单独统计。
- 跨端从最近完成的回答恢复，同场面试限制一端进行语音作答。

## 系统架构与技术选型（推进中，见 system-architecture.md）

- 第 3 步「系统架构图 + 有官方资料依据的技术选型」已产出草案并核对了三家厂商官方能力。
- 已核实的官方事实：DeepSeek 无语音 API（仅文本/视觉）；智谱有 GLM-Realtime 端到端与 GLM-ASR/TTS；阿里有 Paraformer 实时 ASR、CosyVoice 实时 TTS 与 Qwen-Omni-Realtime。
- 已识别的小程序约束：无标准 WebRTC、WebSocket 并发≤5、录音单次≤10 分钟、主包≤2M、域名需 ICP 备案。
- 链路取向建议（待确认）：以「级联 ASR→文本LLM→TTS」为基线，Web 端可试点端到端实时增强。
- 后续待决策：文本 LLM 路由策略、语音供应商主选与互备、Web 登录方案、小程序主体类型、接口与数据模型细化。
